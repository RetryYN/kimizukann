# キミ図鑑 第3回相談会 — 検証版エンジニアリング案

- 対象: 製品企画 v0.3、相談会確定版 v0.4、第2回統合案 v0.5
- 役割: エンジニア
- 前提: 1人開発、Windowsネイティブで開発。検証版はD0〜D12。初期は1プラットフォームのスマホ実機を受入対象とし、クラウドなしで完走する。
- 推奨結論: **Rust製headlessコア＋C ABI＋Flutter描画/UI**。コア状態は原則として整数固定小数点、乱数と走査順を固定する。テストの主戦場はRust CLIとし、スマホUIはD7通過後に接続する。

## 1. 実装技術の選定

## 1.1 headlessコア候補

### 候補A: Rust

利点:

- C/C++級の速度で、64×64×4系統×2,000 tickとseed一括実行に余裕を作りやすい
- 所有権と型で、セル配列、物質移動、状態スナップショットの破壊的な誤りを減らせる
- Windows CLI、Android、iOSへ同じコアをコンパイルできる
- `cargo test`、プロパティテスト、ベンチマークをコアと同じリポジトリで管理できる
- 配列中心のSoA（Structure of Arrays）と明示的な整数演算を実装しやすい

欠点:

- Flutter等とのFFI境界を自分で設計する必要がある
- Rust未経験者には初速が落ちる
- Rustを選んだだけでは浮動小数点の端末間決定性は保証されない
- iOS/Androidビルド、ABI、パニック処理、メモリ所有権の境界試験が必要

判定: **推奨**。計算コアの寿命、seed探索速度、スマホ移植性の釣り合いがよい。

### 候補B: C++

利点:

- Android NDKとiOSで成熟しており、FFI情報が多い
- 性能とメモリ配置を最も細かく制御できる
- Flutter、Swift、KotlinのいずれからもC ABIで呼べる

欠点:

- 境界外アクセス、use-after-free、未初期化、未定義動作が再現性を壊し得る
- 1人開発では安全性とビルド設定の維持コストが高い
- 今回の規模ではRustに対する性能上の決定的な優位が小さい

判定: Rustの習熟が著しく不足している場合の第2候補。新規採用では推奨しない。

### 候補C: Kotlin Multiplatform

利点:

- AndroidとiOSへ共有ロジックを出せる
- Compose Multiplatformを選べばUIとの言語距離が近い
- 型安全で、モバイルアプリの一般機能を作りやすい

欠点:

- JVMとKotlin/Native間の性能、並列処理、浮動小数点、コレクション実装差を意識する必要がある
- 大量seedを回すWindows CLIの速度・運用がRustより読みづらい
- 数値コアとUIの分離が曖昧になりやすい

判定: アプリ機能を優先する初期版には候補だが、headless調整を先行する検証版では推奨しない。

### 候補D: Dartのみ（Flutter内コア）

利点:

- 単一言語・単一ツールチェーンで最短に画面を出せる
- FFIが不要
- 検証用UIの反復が速い

欠点:

- UI isolateと計算の分離、バッチCLI、メモリ配置の最適化が後から課題になる
- コアを別用途へ移植しづらい
- 画面試作の都合で計算契約がUIへ侵入しやすい

判定: クリック可能なモックにはよいが、保存則・seed探索を製品核にする今回は不採用。

### 候補E: TypeScript / WebAssembly

利点:

- ブラウザ可視化と開発ツールが豊富
- headlessスクリプトを書きやすい

欠点:

- 最初の完成形をネイティブスマホアプリとする方針に対し、Web中心の設計へ引かれやすい
- JS数値は基本的に倍精度浮動小数点で、整数固定小数点の上限管理が煩雑
- ネイティブUIとのブリッジを後から足すことになる

判定: 開発者向け結果ビューには使えるが、正本コアにはしない。

## 1.2 推奨コア構成

Rust workspaceを次の単位に分ける。

```text
crates/
  sim-types       状態、ID、固定小数点、設定schema
  sim-core        tick、物質移動、終了判定、PRNG
  sim-events      集計、転換点、evidence_refs
  sim-explain     テンプレート説明、ひとこと仮説判定
  sim-scenarios   環境読込、seedバッチ、分布・ゲート
  sim-ffi         C ABI、バッファ所有権、エラーコード
  sim-cli         run / batch / verify / benchmark
```

依存方向は `types ← core ← events ← explain` とし、UI型をコアへ入れない。`sim-cli`と`sim-ffi`は同じ公開APIを呼ぶ。

### 数値表現

- 物質4プール、生体量、エネルギー、係数は原則 `i64` の固定小数点
- 初期候補は10進6桁スケール（1単位=`1_000_000`）。最大値×tick×セル数の積でオーバーフロー証明をD0に残す
- 乗算は中間値を`i128`へ拡張し、丸め規則を一つに固定
- 拡散で割り切れない残余は、固定された近傍順に配るかセル内残余へ戻し、捨てない
- z-score等の解析だけ浮動小数点を許してもよいが、終了ラベルとコア状態へ逆流させない
- 状態ハッシュは表示状態を除き、正規順序のバイト列から計算する

### 乱数と走査順

- アルゴリズム、バージョン、seed展開を`simulation_contract`へ固定
- PRNG状態をスナップショットへ含める
- セル、系統、近傍、イベントの走査順を固定し、HashMapの反復順へ依存しない
- 1 seed内は原則単一スレッド。並列化はseed間だけにする
- seed番号から独立ストリームを生成し、スレッド数で結果が変わらないようにする

## 1.3 描画/UI層候補

### 推奨: Flutter

Flutterを推奨する理由:

- iOS/Androidを一つのUIコードで出せ、2D培養皿・カード・タイムラインを同じ描画系で作れる
- `CustomPainter`等で集団パッチ、ハッチ、輪郭、表示専用トークンを直接描ける
- OS標準共有、ローカル保存、アクセシビリティを扱いやすい
- コアをC ABIで完全に分離できる

欠点と対策:

- FFI生成ライブラリに強く依存すると更新時の影響が大きい。検証版は小さな手書きC ABIに限定する
- 毎フレーム全状態をコピーしない。コアから描画用スナップショットを固定レイアウトのバッファで受け取る
- シミュレーションはUIスレッドで実行せず、専用isolateまたはネイティブ側のワーカーで進める

FFI公開面は最初、次の6操作程度に限定する。

```text
create(config_bytes) -> handle
step(handle, tick_count) -> status
snapshot(handle, out_buffer) -> length
explain(handle, event_id, out_buffer) -> length
save(handle, out_buffer) -> length
destroy(handle)
```

SwiftUI＋Jetpack Composeを別々に書く案は、各OSの品質は高いが、1人開発でUI工数がほぼ二重になる。初期OSを一つに絞る場合は有力だが、技術決定前の検証版ではFlutterの方が安全である。

## 1.4 テスト基盤

### Rust側

- 単体テスト: 各物質変換、固定小数点、終了判定、理由コード
- プロパティテスト: 非負、物質保存、同seed同ハッシュ、任意tick分割の同値性
- ゴールデンテスト: model_versionごとの固定seed最終ハッシュ、イベント列、説明JSON
- シナリオテスト: 4環境×seed集合、上位互換ゲート
- ファズテスト: config/schema/スナップショット読込、FFI入力
- ベンチマーク: 1 seed、20/100/400 seed、tick p50/p95、スナップショットサイズ

### Flutter側

- Dart単体テスト: 状態管理、仮説選択、カードモデル
- Widget test: 仕込む→放つ→説明→カード→レバーの遷移
- Golden test: 4系統の形状主符号、色なし表示、空き家ハッチ、カード
- Integration test: 実コアを組み込んだ1 seed完走、中断保存・復帰、機内モード
- 実機性能試験: 最低対象端末と基準端末でフレーム時間、消費メモリ、発熱、完走時間

CIが未導入でも、`sim-cli verify`一つでD1〜D9のゲートを順番に実行し、JSONレポートと非0終了コードを返す構造にする。

## 3. 技術リスク上位5つ

### 3.1 リスク1: 同じseedなのに結果が変わる

原因:

- HashMap等の未固定反復順
- seed内並列化による加算順の変化
- PRNG呼出回数が分岐や描画有無で変わる
- コンパイラ・CPUごとの浮動小数点差

回避策:

- コア結果へ作用する値は整数固定小数点
- 配列と列挙順を固定し、seed内は単一スレッド
- 乱数を用途別ストリームへ分ける（移動、繁殖、変異等）。表示は別ストリームまたは決定的ハッシュを使う
- Windows、Android、iOSの同一seed状態ハッシュをmodel_versionごとにゴールデン化
- `step(2000)`と`step(1)×2000`、中断保存後の再開が同一ハッシュになることを必須試験にする

### 3.2 リスク2: 固定小数点の丸めで質量が漏れる、またはオーバーフローする

原因:

- 拡散・摂取の割り算残余を捨てる
- 多数セルの合計、係数乗算、中間値で`i64`を超える
- 負値を0へ丸めて差分を台帳へ戻さない

回避策:

- 中間乗算は`i128`、範囲外は即エラー
- 全変換をfrom/to/amountの台帳関数経由にし、直接代入を避ける
- 丸め残余をセルへ戻すか固定順に分配する
- 各tickの全物質をデバッグビルドで照合、releaseバッチでは規定間隔で照合
- 最大初期量、倍率、2,000 tickの上限証明をD0契約へ置く

### 3.3 リスク3: 64×64×2,000 tickが端末で遅い・熱い

処理量の基準は4,096セル×4系統×2,000 tickで約3,277万セル系統更新。拡散、タグ、集計を含めると数倍になる。

実測目標（初期仮説）:

- 開発PC release: 1 seed 2,000 tick **200 ms以下**、4環境×100 seedを8コアで**30秒以下**
- 最低対象スマホ release: 1 seed 2,000 tick **1.0秒以下**のheadless高速実行
- 通常再生中: シミュレーションtick処理 p95 **4 ms以下**、描画を含むフレームp95 **16.7 ms以下**（60fps目標）
- コア状態＋集計の常駐メモリ **32 MB以下**、D11の保存データ **5 MB以下**
- 10回連続高速実行でクラッシュ、OS強制終了、著しい性能低下なし

回避策:

- SoA連続配列、事前確保、tick内アロケーション禁止
- 変化しないタグと係数を系統別に前計算
- 環境拡散と系統更新の頻度を契約に沿って分ける。ただし最適化前後の状態ハッシュを一致させる
- 描画更新をtickから分離し、最新スナップショットだけ渡す
- D2、D4、D8でベンチを積み上げ、D12で初めて測らない

### 3.4 リスク4: FFIと中断保存で状態が壊れる

原因:

- DartとRustが同じバッファを同時に触る
- handle破棄漏れ、二重解放、アプリ中断中のstep
- スナップショットとmodel_version不一致

回避策:

- FFIは不透明handleとコピーアウトするbyte bufferに限定し、内部ポインタをUIへ渡さない
- すべてのABI関数をpanic境界で包み、エラーコード＋メッセージを返す
- saveはチェックサム、schema_version、model_version、PRNG状態を含む原子的な一塊にする
- 中断処理はstep停止→save→確認→UI側保存の順に固定
- FFIファズ、create/destroy 10,000回、保存途中破損、旧版読込の試験を行う

### 3.5 リスク5: D7のバランス調整が終わらない

原因:

- 系統ベクトル、タグ、環境、終了閾値を同時に動かす
- 代表史を出すために局所補正を足し、一般性を失う
- 100 seedの率だけ合わせ、プレイヤーに見えない結果になる

回避策:

- 一回の調整で変更するパラメータ群を一つに限定
- 各実験のconfig hash、結果分布、変更理由を保存
- ランダム探索より先に感度分析を行い、結果へ効かないパラメータを固定
- 上位互換ゲートと代表史は別判定にし、筋書きのための勝者補正を禁止
- 5日ごとの打切り基準を設け、出ない生命史は期待例側を更新する

## 4. 最初の1週間で作る最小成果物

目標は画面を出すことではなく、**同じ入力が同じ物質史を返し、64×64でも速い**ことを証明する。1週間でD0〜D2の垂直な最小部分を完成させる。

### Day 1: 契約とリポジトリ骨格

- `simulation_contract.md`の状態、単位、tick順、境界条件、丸め、PRNG、走査順を確定
- Rust workspace、`sim-types / sim-core / sim-cli`を作成
- configとresultの最小JSON schema

完了判定: 契約上の各状態がRust型の一フィールドへ対応し、未定義の数値型がない。

### Day 2: 固定小数点と決定性の芯

- 固定小数点型、checked演算、係数乗算、残余処理
- PRNG seed展開と状態保存
- 正規状態ハッシュ

完了判定: 同じseedを100回生成して全状態ハッシュが一致。保存・復元後の次の乱数列が一致。

### Day 3: 1セル閉鎖系

- nutrient→biomass＋waste、維持、死亡→carcassの最小変換
- 2,000 tickの物質台帳

完了判定: 全tickで非負、初期総物質と最終総物質が整数単位で完全一致。意図的な係数誤りでテストが落ちる。

### Day 4: 64×64拡散

- 4近傍、閉境界、固定走査順
- 単一パルスと一様場の試験

完了判定: 2,000 tick後も総物質一致。一様場は不変。左右対称入力は左右対称出力。境界から物質が増減しない。

### Day 5: CLI、ベンチ、証拠レポート

- `sim-cli run --config ... --seed ... --ticks 2000`
- `sim-cli verify`でD1/D2試験
- releaseベンチとJSONレポート
- Windows上で100回の再現試験

完了判定: 次の一コマンドが成功する。

```text
sim-cli verify --suite week1
```

レポートに最低限、model_version、config hash、seed、最終state hash、初期・最終物質量、最大tick時間、2,000 tick総時間を含む。

## 4.1 1週間全体のDone

以下をすべて満たして完了とする。

- 1セルと64×64の両方で2,000 tick物質保存
- 同入力100回で最終state hash一致
- `step(2000)`、`step(1)×2000`、tick 1,000で保存再開の3経路が同一hash
- 64×64×2,000 tick拡散のみが開発PC releaseで200 ms以下を目標。未達でも測定値と上位3ボトルネックが記録されていれば週次成果としては合格、D3着手前に改善判断
- すべての試験がUI、ネットワーク、クラウドなしで実行可能
- JSONレポートだけで別の人が合否を確認できる

### 1週間で作らないもの

- スマホ画面、カード、トークン
- 4系統のバランス
- 転換点と説明器
- 生成AI連携
- 分岐、コドン、通知、バックグラウンド進行

この週の価値は「見た目」ではなく、以後のすべてを載せられる決定的な計算基盤を、小さく反証可能な形で作ることにある。
