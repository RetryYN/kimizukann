# キミ図鑑 第3回相談会 ラウンド2 — Codex回答

- 対象: `docs/00_product/第3回_検証版計画_v1.0.md`
- 役割: エンジニア
- 結論: 技術、工程、初週成果物の採用はほぼ正確。初期OSは **Android**、配布は最初の8〜12人に限り **署名済みAPK直配布**を推奨する。速度は低速1／標準4／高速16 tick/sとする。ただしwall clockを決定的コアへ入れず、再生スケジューラ契約として分離する。

## 1. 1章・2章・4章の採用状況

### 1.1 正しく採用されている点

- Rust、i64固定小数点、中間i128、整数残余を捨てない方針は意図どおり。
- seed内単一スレッド、走査順固定、用途別乱数、三経路一致は決定性の中心を正しく捉えている。
- Flutterと小さなC ABI、固定レイアウトの描画バッファという分離も意図どおり。
- 68〜102人日、中央値85人日、D7の別バッファという計画は、見積もりの幅を不当に縮めていない。
- D7合格まで本UIへ進まないこと、静的描画・FFIスパイクだけを1〜2日許すことに異論はない。
- 初週Doneは、見た目ではなく決定性、保存則、性能を証拠JSONで示す内容になっている。
- P0から検証目的外の顕微鏡・共有拡張等を外した判断は妥当。

### 1.2 修正が必要: FFIに復元操作がない

1章はFFIを `create / step / snapshot / explain / save / destroy` の6操作としているが、D12は中断復帰を必須にしている。`save`した状態からhandleを復元する操作がない。

次のいずれかが必要である。

```text
load(save_bytes) -> handle
```

または、createを二種類の入力へ対応させる。

```text
create_from_config(config_bytes) -> handle
create_from_save(save_bytes) -> handle
```

APIの意味が明確なため、7操作目として`load`を追加する案を推奨する。`load`はchecksum、schema_version、model_versionを検証し、不一致をエラーにする。「6操作に限定」は「小さな7操作に限定」へ修正する。

また、可変長出力は必要サイズを問い合わせられる契約か、コア側が確保して専用の`free_buffer`で解放する契約が必要である。後者は操作数と所有権を増やすため、検証版は呼出側がバッファを渡し、容量不足時にrequired lengthを返す方式がよい。

### 1.3 修正が必要: D10をP1にするとクリティカルパスと矛盾する

4章ではD10「パッチ＋トークン描画」をP1としているが、2章のクリティカルパスはD10からD12へ合流し、D10の完了判定も正式に定義されている。さらにテスト質問1の「皿のどこが変わったか」には最低限のパッチ描画が必要である。

次のように分ける。

- **P0**: 4系統の集団パッチ、形状主・色補助、資源・死骸・waste、空き家、スタンプ位置、計算非干渉ハッシュ
- **P1**: 最大8個の表示専用トークンと局所演出

D10自体はP0とし、P1トークンを無効化してもD12のテストを実施できるようにする。これなら「トークンを消しても終了ラベルが一致」という非干渉試験も残せる。

### 1.4 軽微な修正: P0の優先順

表ではD10がD11より下のP1に見えるが、実装順は次が自然である。

```text
D8 → D9
       ├→ D10 最小描画
       └→ D11 seed選定
D10 + D11 → D12
```

D11のheadless選定はD10なしでもできるため並行可能だが、初見で転換点が視認できるかの最終選定は最小描画上で再確認する。

## 2. 論点K — 初期OSとテスター配布

### 結論

初期OSは **Android**。最初の8〜12人には **release署名済みAPKを直接配布**する。D12と初回ユーザーテストが通った後、継続テストではGoogle Playの内部テストへ移す。

### 理由

現在の開発環境はWindowsネイティブである。Flutterの公式手順では、iOSのビルドとリリースにXcodeとmacOS端末が必要であり、現在の環境だけでは完結しない。[Flutter公式: Build and release an iOS app](https://docs.flutter.dev/deployment/ios)

AndroidはWindows上でFlutterのビルド、RustのAndroidターゲット、実機接続、署名APK生成まで行える。少人数の既知テスターなら、APKをファイルで渡し、端末側で提供元を許可してインストールできる。Googleも、正式なテストトラックとは別に、信頼できるテスターへ非公式チャネルで共有する場合があることを案内している。[Android Developers: Build and test your Android App Bundle](https://developer.android.com/guide/app-bundle/test)

一方TestFlightは、インストール体験とフィードバック収集は優れているが、iOSビルドにmacOS/Xcodeが必要で、外部テスター向けの初回ビルドにはTestFlight App Reviewが必要となる。Apple公式も、外部テストでは最初のビルド承認が必要と案内している。[Apple Developer: TestFlight Overview](https://developer.apple.com/help/app-store-connect/test-a-beta-version/testflight-overview/)

### APK直配布とTestFlightの比較

| 項目 | Android署名APK直配布 | iOS TestFlight |
|---|---|---|
| 現在のWindows環境 | 完結可能 | macOS＋Xcodeが必要 |
| 配布開始まで | ビルド・署名後すぐ | App Store Connect登録、アップロード、初回外部審査 |
| テスター側 | 提供元許可が必要で多少不安 | TestFlight経由で分かりやすい |
| 更新 | APKを再配布 | TestFlightで更新管理しやすい |
| フィードバック | 別途聞き取り | スクリーンショット・クラッシュ報告が統合 |
| 8〜12人の一次知人 | 十分 | 運用がやや重い |

### APK配布の最低契約

- debug APKではなくrelease署名APK
- package ID、versionName、versionCodeを固定規則で更新
- SHA-256とビルド日時、model_versionを配布メモへ記載
- APKは個別の信頼できる経路で渡し、一般公開リンクに置かない
- インストール手順とアンインストール手順を1ページにする
- ユーザーデータはアプリ専用領域だけに保存し、不要な権限を要求しない
- テスト終了後、提供元許可を戻せることを案内する

### Androidを選ぶことの限界

これは市場優先OSの決定ではなく、検証版を現在の開発環境で最短配布する技術判断である。日本の8〜12人の候補端末がiPhoneへ極端に偏る場合は、Androidユーザーを募集するかMacを正式に用意して再判断する。Flutter採用なのでiOS移植性は維持するが、「Androidで動いたからiOSでも同じ」とは見なさず、Rust状態ハッシュとFlutter描画のiOS実機試験を別ゲートにする。

## 3. 論点L — 再生速度と10分完走

### 3.1 契約を置く層

tick/sはシミュレーションの決定的コアではなく、**再生スケジューラ**の契約にする。コアはwall clockを一切読まず、`step(n)`で要求されたtick数だけ進める。同じseedと操作列なら、端末速度や描画fpsに関係なく同じ状態になる。

`simulation_contract.md`には、論理時間換算と再生プリセットを記載してよいが、コア更新式はtick/sを参照しない。

### 3.2 推奨3段階

| モード | 契約tick/s | 2,000 tickの連続再生時間 | 用途 |
|---|---:|---:|---|
| 低速 | **1 tick/s** | 約33分20秒 | 転換点周辺を細かく観察する。一時的利用 |
| 標準 | **4 tick/s** | 約8分20秒 | 初回の基本。10分枠へ約100秒の操作余白を残す |
| 高速 | **16 tick/s** | 約2分5秒 | 既知部分の早送り、再実験 |

標準を3.33ではなく4 tick/sにする理由は、説明を開く、仮説を選ぶ、カードを見る時間を10分枠内に残すためである。100世代相当は2,000 tick上限から表示換算する。

### 3.3 高速上限

検証版のユーザー操作で選べる高速は **16 tick/sを上限**とする。

- 転換点集計は10 tickごとなので、16 tick/sなら集計点が約0.625秒ごとに進む
- 重要な変化を完全に瞬間移動させず、スタンプ発生を視認しやすい
- 1フレームあたりのstep数を小さく保て、描画と入力を止めにくい

コアのheadless性能目標「2,000 tickを1秒以内」は、再生上限ではない。seed探索、D7バッチ、保存後の短いリプレイ専用であり、ユーザーの観察再生へそのまま公開しない。

### 3.4 スケジューラ規則

- シミュレーションtickは固定時間刻み。実フレーム時間を更新式へ掛けない
- schedulerは経過wall timeから「実行すべきtick数」を整数で算出
- 1描画フレームで実行する上限を低速1、標準1、高速2 tick程度にし、遅れは次フレームへ持ち越す
- 端末が追いつかない場合、描画を間引き、tickを捨てない
- 500 ms以上遅れが累積したら速度表示へ「端末が追いついていません」を出し、自動的に一段下げる
- 一時停止、説明表示、OS中断中はtickを進めない
- 速度変更はPRNGを消費せず、結果へ影響させない。低速・標準・高速で最終state hash一致を必須試験にする

60fps時の平均tick配分は、標準なら15フレームに1 tick、高速なら約3〜4フレームに1 tickであり、十分な余裕がある。30fps端末でも高速は約2フレームに1 tickである。

### 3.5 「10分完走」の正確な定義

ユーザーが無制限に一時停止や低速を選べる以上、wall clockで必ず10分以内とは保証できない。保証文は次のように限定する。

> 基準端末で、標準速度、手動停止なし、OS中断なしの場合、2,000 tickを8分20秒以内に再生し、開始前操作と終了表示を含む標準一巡を10分以内に収める。

加えて高速については、次を性能受入とする。

> 最低対象端末で、高速16 tick/s、手動停止なし、OS中断なしの場合、2,000 tickを2分10秒以内に再生する。処理遅延によりこの時間を超える端末は対象外または自動的に描画品質を下げる。

初見テストでは標準速度から開始し、低速はスタンプ選択時の一時観察に限定して案内する。ユーザーが低速を長く使った場合はテスト失敗ではなく、実際の完了時間と速度利用履歴を記録する。

## 4. 追加の受入試験

- 同じseedを低速・標準・高速で最後まで進め、状態ハッシュ、終了ラベル、イベント列が一致
- 30/60/90/120 Hzの模擬フレーム列で、同じwall time後のtick番号が許容差内
- 1秒の描画停止後もtickの順序を保ち、UIが復帰する
- 高速中にスタンプが発生しても重複表示せず、タイムラインへ同じevent_idが一件だけ残る
- Android最低対象端末で標準8分20秒、高速2分10秒の再生上限を実測
- アプリ中断・復帰を速度3段階で行い、保存前後のstate hashが連続
