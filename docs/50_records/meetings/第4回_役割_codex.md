- 前提: 検証版D0〜D12はClaude Code / Codex / CursorのAIチームで実装する
- 人間オーナー: yoshiyuki。製品判断、権限・秘密情報、実機とテスター調達を担当
- 評価方針: モデルの一般能力ではなく、このプロジェクト、このCodexセッション、このWindowsワークスペースで実際に遂行できることを基準にする

## 1. Codex自身の得意分野

### 1.1 決定的な計算コアの設計と実装

Rustの型、整数固定小数点、`i128`中間演算、丸め残余、PRNGストリーム、固定走査順を、契約・コード・テストの三点へ同時に落とす作業が得意である。D0〜D4のように、不変条件を先に定義して小さく実装し、反例テストで固める仕事に向く。

### 1.2 不変条件・再現性・境界条件のテスト

物質保存、非負、`step(2000)`と分割stepの一致、中断再開、同seed同hash、描画非干渉など、「何が同じでなければならないか」を列挙し、自動テストへ変換できる。バグを症状ではなく、破られた契約から追う作業に強い。

### 1.3 CLI・バッチ・検証レポートの自動化

seed一括実行、JSON分布、ベンチマーク、非0終了コード、回帰fixtureなど、D6/D7を人手の表計算にしないための仕組みを作れる。PowerShell上でコマンドを実行し、ログと出力を確認しながら修正できる。

### 1.4 技術設計の構造化と矛盾検出

企画文の要件を状態、操作、保存、失敗条件、性能予算へ翻訳し、欠けた`load`操作や優先度とクリティカルパスの矛盾などを見つけられる。コア、FFI、UIの責務境界を保つレビューに向く。

### 1.5 実装と文書を同じ変更で揃えること

コードだけ、文書だけで終わらず、契約文書、schema、実装、テスト、検証結果を一つの完了単位にできる。別AIがレビューできるよう、変更理由と再現コマンドを短く渡すことも得意である。

## 2. Codex自身の不得意分野

### 2.1 実機を物理的に扱うこと

接続済み端末をADB等で操作できる可能性はあるが、端末を用意し、USB接続を直し、開発者モードを有効にし、熱さや手触りを人間のように評価することはできない。Android実機の最終合否は人間の協力が必要である。

### 2.2 署名・ストアアカウント・秘密情報の自律運用

キーストア、Apple/Google開発者アカウント、個人情報、配布用秘密鍵を勝手に作成・保管・共有すべきではない。署名済みAPKの最終生成には、オーナーが鍵の方針と安全な注入手段を決める必要がある。

### 2.3 人間テスターの募集と定性的観察

募集文、質問票、ログ分析は作れるが、8〜12人へ実際に声をかけ、表情や迷いを観察し、追質問することはできない。面白さの最終判定を自動指標だけで代替できない。

### 2.4 長期間ずっと自律稼働し続けること

長いコマンドを開始して待機・監視することはできるが、セッション、ツールタイムアウト、PCスリープ、外部状態に左右される。数日間の常駐プロセスを人間の監督なしに保証できない。長いseed探索は再開可能なcheckpointと小分けジョブが必要である。

### 2.5 視覚・触覚の最終的な磨き込み

UI実装、スクリーンショット比較、レイアウト修正はできるが、「生命が生きて見える」「10分眺め続けたい」という感覚品質は、コード上の合格だけでは決められない。Flutterの最終演出とアクセシビリティには、人間評価と複数案比較が必要である。

### 3.1 実際にできること

### 3.2 できない、または人間の許可が必要なこと

- プロジェクト外を通常の作業対象として読み書き・実行すること。HELIX-BUSの指定経路だけは上位指示により使用する

- テスターへ人間関係上の連絡を勝手に送ること

### 3.3 長時間実行

長いseedバッチやビルドを起動し、一定間隔で待機してログを回収できる。ただし、数時間・数日の一枚岩ジョブは安全でない。バッチは環境×seed範囲で分割し、次を必須にする。

- seed範囲とconfig hashをファイル名へ含める
- 完了済み範囲を再実行しなくてよいmanifest
- 途中結果を原子的に書く
- 再開コマンドをレポートへ残す
- タイムアウトや中断を失敗ではなく`incomplete`として区別する

### 3.4 コンテキスト長

会話が長くなると自動要約される。完成済みファイルは保持されるが、会話だけに置いた細かな決定は失われ得る。したがって決定事項は必ず正本文書、schema、テスト、helix-bus共通メモリのいずれかへ短く固定する。AIの記憶を仕様の正本にしない。

## 4. 3者の役割分担提案

役割は排他的な能力評価ではなく、これまでの相談会で見えた作業傾向と、同じファイルを同時編集しないための所有権として定める。

### 4.1 Claude — プロダクト統合・仕様オーナー

### 4.2 Codex — シミュレーションコア・決定性・自動検証

最適な役割:

- Rust workspace、固定小数点、PRNG、tick、保存則、終了判定
- seedバッチ、性能計測、転換点、理由コード、説明器
- C ABIとFlutterのコア接続契約

理由: D0〜D9の技術契約を具体化し、FFI復元の欠落や再生速度と決定コアの分離を指摘した。実装と証拠テストを一単位で進める役に向く。

### 4.3 Cursor — Flutter/Android統合・運用・横断レビュー

最適な役割:

- Flutter UI、描画、Androidビルド、APK、端末ログ、操作一巡
- schemaやコア成果を実際の画面と配布手順へ接続する
- D0〜D9の契約に対する実装レビュー、とくに未定義定数・保存量・運用穴の検出

理由: 第2回で状態名、tick順、係数、閾値、保存量まで契約化し、第3回ではテスター運用を具体化した。IDEに近い位置でUI・ビルド・運用を横断する役が適している。

## 6. 3者で回す作業プロトコル

## 6.1 一作業の基本単位

一つの作業は次の順序で回す。

1. **Claudeがtask briefを投函**
   - task ID（例 `D2-diffusion-001`）
   - 入力となる正本ファイルと章
   - writer、reviewer
   - 変更可能ファイル一覧
   - 完了判定コマンド
   - 禁止事項、期限ではなく打切り条件
2. **主担当が開始通知**
   - `started: task ID / files / assumptions`
   - ファイル所有権を宣言
3. **主担当が実装**
   - 契約→テスト→コードの順
   - 長い実行はcheckpointを残す
4. **主担当がresultを投函**
   - 変更ファイル
   - 実行コマンド
   - pass/failと主要数値
   - 未解決事項
5. **reviewerが独立確認**
   - 差分を読む
   - 同じコマンドまたは独立した反例テストを実行
   - `approve / changes_requested / blocked`を返す
6. **Claudeが統合判定**
   - 正本更新
   - 次段階へ進むか、主担当へ差し戻す

## 6.2 busメッセージ形式

自由文だけにせず、本文冒頭を揃える。

```text
[D2-diffusion-001][started]
writer=codex
files=crates/sim-core/..., docs/simulation_contract.md

[D2-diffusion-001][result]
status=pass
command=cargo test ...
evidence=artifacts/verify/...
open_issues=none

[D2-diffusion-001][review]
status=changes_requested
finding=境界セルで残余1単位が失われる
repro=...
```

共通メモリへは、長い結果ではなく「今後も有効な決定」だけを追加する。ログやスタックトレースはプロジェクト内artifactへ置き、busにはパスを送る。

## 6.3 コンフリクト回避

- 一ファイル一writer。reviewerはレビュー中に対象ファイルを直接直さない
- タスク開始時に変更可能ファイルを列挙し、共有ファイルの所有権を宣言
- `simulation_contract.md`、schema、Cargo lockfile、Flutter pubspecは共有ホットスポットとしてClaudeが編集順を管理
- reviewerの修正案は別レビュー文書またはbusで返し、writerが反映する
- 緊急の小修正でも、writerへ所有権移譲を通知してから編集する
- 未コミット変更を前提にし、破壊的なGit操作を使わない

## 6.4 レビュー粒度

段階全体を一度にレビューせず、次の順に小さく切る。

- 契約・型
- 正常系の最小実装
- 不変条件・反例
- 性能
- 保存・互換
- UI接続

D1〜D4は一PR相当300〜500行程度を目安に分割する。巨大な生成ファイルやfixtureは行数に含めないが、生成手順とhashを付ける。レビュー完了前に次の段階の同じ領域へ進まない。

## 6.5 長時間作業と待機

- 100 seedを一ジョブにせず、環境×20 seed等へ分割
- 実行開始時にjob manifestを作る
- 完了ごとに結果を原子的に保存
- AIが待機へ戻っても、別AIがmanifestから状態を確認できる
- 割り込み指示を各チャンク境界で確認する
- 同じ失敗を3回繰り返したら、ログ付きでClaudeへ設計判断を求める

## 7. 人間オーナーに求めること3つ

### 7.1 製品判断と打切り

D7で「期待した物語のためにモデルを変えるか、自然に出た別の物語を採るか」、D11で「この10分を人へ見せるか」を決めてほしい。AIはデータと選択肢を提示できるが、面白さと製品らしさの最終責任はオーナーにある。

### 7.2 実機・署名・テスターの用意

- 初期対象のAndroid実機、最低対象に近いミドルレンジ端末
- APK署名鍵の安全な作成・保管方針
- 8〜12人のテスター募集、日程調整、同意、聞き取り

AIへ秘密鍵そのものを会話やGitで渡さず、安全なローカル注入方法を決めてほしい。

### 7.3 優先順位変更の明示

開発途中で新機能を思いついた場合、それが検証版P0を止めてでも必要か、初期版候補へ置くかを明示してほしい。AIチームへ同時に異なる指示を送らず、変更はClaudeのtask briefまたは正本更新を通して一本化してほしい。

## 8. 推奨するチーム原則

AIチームだから人間より速い部分はあるが、D7の創発調整、D10の見やすさ、D12の面白さは単純に3倍速にはならない。3者の価値は同じコードを同時に書くことではなく、**一人が書き、一人が壊しにかかり、一人が製品目的との整合を判定すること**にある。

主担当の自己申告だけを合格根拠にせず、必ず再現コマンド、機械判定、別AIレビュー、人間が必要な箇所の目視判定を揃える。
