# キミ図鑑 v0.3 システム合理性レビュー

- 対象: `docs/00_product/製品企画.md`（製品企画 0.3）
- 役割: システム合理性担当
- 結論: コアループは成立し得る。ただし「個体をどこまで直接計算するか」「保存則をどの単位で保証するか」「説明可能性をシミュレーションへどう埋め込むか」を先に決めないと、面白さ検証版が使い捨てになる。初期版には、空間をセルへ離散化した集団ベースモデルを推奨する。

## 1. 矛盾・未定義・実装困難点

### 1.1 物質循環の閉じ方が未定義（3章、6章）

- 問題: 3章は資源、摂取、代謝、死骸、環境変化を要求し、6章は質量・エネルギー収支を破綻させないとしている。しかし、追跡する物質、外部流入、廃棄物、熱散逸、培養皿が閉鎖系か開放系かが決まっていない。
- なぜ困るか: 保存則の単位がなければテスト不能である。全物質を厳密に追うと重くなり、単一の「資源値」だけでは毒化、死骸利用、代謝コストを説明しにくい。
- 解決案: 初期版は `栄養資源 / 生体量 / 死骸 / 老廃物` の4プールに限定する。エネルギーは独立粒子にせず、各変換の効率と熱損失として台帳化する。各tickで `流入 + 前tick総量 - 流出 - 現tick総量 = 許容誤差内` を検証する。培養皿は原則閉鎖系とし、プリセットでのみ一定流入を許す。

### 1.2 「100世代」の時間定義が曖昧（3章、4章）

- 問題: 個体ごとに繁殖周期や早期繁殖形質が異なるのに、培養全体を約100世代と呼んでいる。
- なぜ困るか: 非同期繁殖では全系統共通の世代番号が存在しない。終了条件、ログ表示、性能予算、系統固定判定が揺れる。
- 解決案: 内部時間はtickで統一する。表示上の「世代」は、基準型の平均繁殖周期を1世代とする換算値にする。系統ごとの実世代数は別に記録する。初期検証は例えば2,000 tickを上限とし、全滅・固定・時間上限のいずれかで終了する。

### 1.3 形質の利益とコストが文言だけでは比較不能（4.2、5.1）

- 問題: 高速移動、高効率摂取、低維持コスト、早期繁殖、死骸利用の例はあるが、共通予算と制約式がない。
- なぜ困るか: 個別に数値調整すると隠れた上位互換が生まれやすい。組合せが増えるたびにバランス調整量が爆発する。
- 解決案: 形質を、移動・摂取・変換・維持・繁殖へ作用する倍率として定義し、各形質に生体量またはエネルギーの明示コストを課す。初期適応方針は一つの長所と一つ以上の短所を持つ固定ベクトルにする。全方針を同じ環境で同等勝率にするのではなく、環境ニッチごとの優位性が入れ替わることを受入条件にする。

### 1.4 系統・形質・種分化の境界が未定義（3章、7.1、13章）

- 問題: 系統固定、分岐、突然変異、遺伝を要求しているが、個体差がいつ別系統になるか決まっていない。
- なぜ困るか: 小さな連続変異で系統数が無限に増えるか、逆に初期4系統から永遠に分岐しない。図鑑カードと説明の主語も安定しない。
- 解決案: 初期版では形質を少数の離散アレルに限定する。遺伝的距離、一定以上の個体数、一定期間の再生産継続、親集団との交雑または機能ニッチ差の条件を満たしたクラスターだけを「分岐候補」とする。表示系統IDは判定確定時に発行する。

### 1.5 3種類の結果を「作為なし」に出す要件は無制約では保証不能（8.2）

- 問題: 優勢系統の衰退、劣位系統の逆転、seedによる固定・共存・全滅を、固定イベントなしで発生させるとしている。
- なぜ困るか: 創発結果はパラメータ領域に依存し、任意seedや短時間で3結果すべてを保証できない。保証しようとすると、裏で結果を誘導する固定イベントになり得る。
- 解決案: 「任意の一回で発生」ではなく、「承認済み初期条件とseed集合に対する統計的受入」へ変更する。例えば100 seed中、固定20%以上、共存10%以上、全滅5%以上、逆転イベント10%以上といった発生帯を定義する。イベントを注入せず、探索ツールで条件とseedを発見・固定して回帰試験にする。ユーザーには結果を保証しない。

### 1.6 説明生成に必要な因果情報が状態スナップショットだけでは足りない（4.5、7.1）

- 問題: 事実、有力な解釈、未知、次の一手を表示するとしているが、何を因果とみなすか未定義である。
- なぜ困るか: 個体数グラフの相関だけから「資源枯渇が原因」と断定すると誤説明になる。端末上で生成AIへ丸投げすると、オフライン完走、再現性、科学的区分を損なう。
- 解決案: シミュレーションコアが各状態変化へ理由コードと寄与量を記録する。説明器は、イベントログ、変化点、寄与量、反実仮想の簡易再計算からテンプレートを選ぶ。生成AIは将来、文章の言い換えに限定し、事実認定には使わない。

### 1.7 端末内完走とバックグラウンド継続の関係が未整理（4章、7.1、12章）

- 問題: 7.1は端末内完走を必須とする一方、12章では標準時間とバックグラウンド進行が未決定である。OSは長時間のバックグラウンド計算を保証しない。
- なぜ困るか: アプリを閉じても精密なシミュレーションを継続する設計は、電力、熱、OS制限、再現性に抵触する。
- 解決案: 初期版はフォアグラウンドで10分以内に完走する。中断時は状態とPRNG状態を保存し、復帰後に再開する。将来の放置進行は、経過時間をそのままtick実行せず、集約モデルで追いつく別仕様として扱う。

### 1.8 保存・再現の契約が不足（4.6、4.7）

- 問題: 条件とseedを保存し同seed再現を求めるが、アプリ版、モデル版、浮動小数点差、更新後の互換性が定義されていない。
- なぜ困るか: 同じseedでも実装や演算順序が変われば結果が変わる。生命史カードの再現性を永続保証すると更新が困難になる。
- 解決案: カードへ `model_version / parameters_hash / initial_state / PRNG_algorithm / seed` を保存する。同一モデル版内のみビット単位または判定単位の再現を保証する。旧モデルは結果ログの閲覧を保証し、再実行時は旧エンジン保持または「現行モデルで再解釈」を明示する。

### 1.9 「最低4系統」と画面可読性の競合（3章、5.5）

- 問題: 4系統に加えて変異・分岐・資源・毒性・死骸をスマホ画面で同時に読ませる。
- なぜ困るか: 色だけでは系統、状態、物質を同時符号化できず、色覚差にも弱い。粒子数が多いほど出来事が視覚ノイズになる。
- 解決案: 系統は色と輪郭形状の二重符号、状態はアニメーション、環境場は切替レイヤーに分ける。通常表示は個体ではなく集団パッチを描画し、重要イベント時だけ局所を拡大する。表示オブジェクト数を計算粒度と切り離す。

## 2. 計算量見積もりとモデル粒度

### 2.1 前提となる性能予算

10分の体験で2,000 tickを進めると仮定する。標準速度なら毎秒約3.3 tick、高速時に10〜20倍を許す。ミドルレンジ端末で描画を含めて安定させるには、シミュレーションへ割り当てるCPU時間を標準時で1tickあたり概ね5〜10 ms以下、高速時は描画間引きを前提に20〜30 ms以下とするのが安全である。メモリはコア状態とログを合わせて数十MB以内を目標にする。

### 2.2 個体ベースモデルの概算

個体数を `N`、近傍探索を空間グリッドで平均近傍数 `k` とすると、1tickは概ね `O(N × k)` である。素朴な全個体間相互作用は `O(N²)` なので不可である。

例えば最大10,000個体、平均近傍8、2,000 tickなら約1.6億回の近傍評価になる。単純演算だけならネイティブ実装で可能性はあるが、経路探索、衝突、遺伝子オブジェクト、詳細ログ、描画を加えると低価格端末で不安定になる。10万個体では現実的でない。個体数の増減が処理時間へ直結し、繁栄した結果ほど遅くなる点も体験上悪い。

### 2.3 個体群ベースモデルの概算

培養皿を例えば64×64=4,096セルへ分割し、各セルに4〜8系統の集団量と形質クラスを保持する。1tickの主要処理は拡散・移動・摂取・繁殖について `O(C × L × T)`、`C`はセル数、`L`は系統数、`T`は少数の形質クラスである。

4,096セル×4系統×2形質クラス×2,000 tickで約6,550万セル系統更新となる。処理配列が連続し、分岐が少ないため高速化しやすい。空セルをスキップする疎表現、低頻度処理の分離、環境場の更新間引きでさらに削減できる。計算量の上限が個体数爆発に左右されにくい。

### 2.4 推奨

初期版は**空間セル上の個体群ベースモデル**を推奨する。各セル・系統について、個体数または生体量、平均エネルギー、形質クラス別比率を保持する。見た目には集団量から代表個体をサンプリング描画し、個体が動いている感覚を出す。

個体ベースは、希少な捕食、突然変異の発生、創始者イベントなど、物語上重要なイベントだけを「トークン個体」として重ねるハイブリッド方式がよい。これにより空間的な逆転や系統分岐を残しつつ、性能上限と保存則を管理できる。

推奨初期上限は次のとおり。

- 空間: 64×64セル（端末性能で表示解像度のみ変更し、計算解像度は固定）
- 初期系統: 4、同時表示系統上限8
- 形質: 5軸以内、各軸2〜3段階
- 内部時間: 最大2,000 tick
- 環境プール: 栄養、生体量、死骸、老廃物
- 転換点用集計: 10 tickごと、最大200サンプル
- 詳細イベントログ: 上限件数を設け、集約前後値と理由コードだけを保存

## 3. 転換点検出と説明生成

### 3.1 記録するデータ

各10 tickの観測窓で、系統ごと・領域ごとに次を集計する。

- 生体量、個体数相当、出生、死亡
- 摂取量、維持消費、繁殖投資
- 死因別死亡量（飢餓、捕食、毒性など）
- 資源、死骸、老廃物
- 捕食・死骸利用など相互作用別の物質フロー
- 形質クラス比率、遺伝的距離
- 各更新式の寄与量と理由コード

重要なのは「現在値」だけでなく、「何によって増減したか」というフロー台帳を持つことである。

### 3.2 転換点の検出

固定イベントを置かず、時系列から次を検出する。

1. 指標を移動平均との差または変化率へ変換する。
2. 閾値を一定値だけでなく、直近分散に対するz-scoreと継続時間で判定する。
3. 複数指標が近い時刻に変化した場合、一つのイベント候補へまとめる。
4. イベント前後の寄与量を比較し、支配的なフローを抽出する。
5. 小さな揺らぎを抑えるため、重要度を `変化量 × 継続時間 × 影響した系統数` で順位付けする。

例として、資源量の急減が先行し、その後に系統Aの摂取不足と飢餓死が増えた場合、「資源枯渇に続くAの衰退」を候補にする。単に同時に減っただけなら「関連が疑われる」に留める。

### 3.3 有力な解釈の生成

解釈は次の三段階で作る。

- 機構候補: 理由コードとフロー台帳から、増減へ寄与した上位要因を列挙する。
- 時系列整合: 原因候補が結果より前に変化しているか、作用する系統・領域が一致するかを確認する。
- 簡易反実仮想: イベント直前の小さな状態コピーを短時間だけ再計算し、候補要因を基準値へ戻した場合に結果が弱まるか調べる。

反実仮想で差が明確なら「有力」、時系列と機構だけなら「可能性」、候補が競合するなら「複数要因・不明」と表示する。完全な因果証明とは呼ばない。

### 3.4 表示文の構造

テンプレートは次のデータ構造から生成する。

```text
観測事実: 62〜71世代相当で、系統Aの生体量が38%減少した。
有力な解釈: その直前にAの主要領域で栄養が64%減り、死亡量の71%が飢餓由来だった。
まだ不明: 系統Bとの競争も同時に強まり、影響を完全には分離できない。
次の一手: Aの初期個体数だけを20%減らし、資源枯渇が遅れるか再実験する。
```

「次の一手」は、候補原因へ対応する操作可能変数を一つだけ選ぶ。変更幅は事前に安全な小・中・大の三段階を定義する。同seedで再実行して局所効果を比べ、その後に別seedで頑健性を確認する導線にする。

### 3.5 説明器のテスト

- 同一ログから常に同じ説明を生成する決定性テスト
- 数値と文言が一致する根拠参照テスト
- 原因より結果が先行していないかの時系列テスト
- 複数要因時に断定表現を避ける校正テスト
- 既知の合成シナリオで期待する理由コードが上位に来る回帰テスト
- シミュレーション版更新時の説明差分テスト

## 4. 13章「次の企画判断」の優先順位

手戻りの大きい順に並べる。

### 1位: 培養皿の資源配置と物質循環（項目2）

状態モデル、保存則、性能、可視化、説明のすべてを決める土台である。物質プールと変換式を先に固定する。

### 2位: 4系統それぞれの特徴、利益、コスト（項目1）

循環モデル上で何をトレードオフにするかを決める。ここが曖昧だと勝敗も説明も設計できない。

### 3位: 系統固定、分岐、共存、全滅の判定条件（項目7）

終了条件、図鑑記録、受入テスト、seed探索に直結する。実装後に変更すると既存ログとシナリオが無効になる。

### 4位: 100世代で起き得る代表的な生命史（項目4）

上位3項目を使って、期待する創発領域を統計的に定義する。単発の台本ではなく、seed集合と発生率で記述する。

### 5位: 転換点を検出するルール（項目5）

必要な集計項目とログ粒度を確定する。コア実装後でも調整できるが、元データを記録していなければ遡れないため早期に最低限を決める。

### 6位: 「今どうなってる？」が返す説明の形式（項目6）

企画書の4区分はすでに良い。文面は後から変えられるため、先に説明根拠のデータ契約を決め、UI文言は試作で磨く。

### 7位: プレイヤーが選べる適応方針（項目3）

操作項目は重要だが、内部モデルのうち安全に公開できるつまみとして最後に選ぶべきである。先にUI上の選択肢を固定すると、シミュレーションをその選択肢へ無理に合わせることになる。

## 5. 推奨する次の成果物

実装着手前に、企画書とは別に次の三点を作ることを推奨する。

1. **simulation_contract.md**: 状態、単位、物質変換式、tick、乱数、保存則、終了判定。
2. **reference_scenarios.json**: 初期条件、seed集合、期待する結果分布、許容範囲。
3. **explanation_contract.md**: 理由コード、集計窓、転換点、根拠データ、確信度、文テンプレート。

最初の実装順は、描画より先にheadlessコア、保存則テスト、seed一括実行、転換点ログを作る。その後、代表個体の描画とスマホUIを載せる。これなら「面白いか」を測るための調整を高速に回しつつ、端末内完走へそのまま接続できる。
