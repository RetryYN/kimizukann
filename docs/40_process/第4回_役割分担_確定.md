## 4. 作業プロトコル（3 者案の統合）

### 4.1 一作業の単位（Codex 6.1 を採用）
1. **Claude が task brief を投函**：task ID（例 `D2-diffusion-001`）、入力正本と章、writer／reviewer、変更可能ファイル一覧、完了判定コマンド、打切り条件
2. **writer が `started`**：files と assumptions を宣言（所有権）
3. **writer が実装**：契約→テスト→コードの順。長い実行は checkpoint
4. **writer が `result`**：変更ファイル、コマンド、pass/fail と主要数値、open_issues
5. **reviewer が独立確認**：差分を読み、同じコマンドまたは反例テストを実行 → `approve / changes_requested / blocked`
6. **Claude が統合判定**：正本更新、次段階の brief 発行または差し戻し

### 4.2 bus メッセージ形式（Codex 6.2）
```
[D2-diffusion-001][started]  writer=codex  files=...
[D2-diffusion-001][result]   status=pass  command=...  evidence=artifacts/verify/...  open_issues=none
[D2-diffusion-001][review]   status=changes_requested  finding=...  repro=...
```
共通メモリには「今後も有効な決定」だけ。ログ・トレースは `artifacts/` に置きパスを送る。

### 4.3 所有権とコンフリクト回避（Cursor 4 ＋ Codex 6.3）
- crate 所有：`sim-core / sim-types / sim-events / sim-scenarios / sim-ffi / sim-cli` ＝ Codex、Flutter `lib/` ＝ Cursor、`docs/` の企画・契約統合 ＝ Claude、`docs/50_records/meetings/` の自分のファイル ＝ 各自
- 共有ホットスポット（`simulation_contract.md`、schema、`Cargo.lock`、`pubspec`）は Claude が編集順を管理
- reviewer はレビュー中に対象ファイルを直接直さない。修正案は bus で返し writer が反映
- **git を導入する**（オーナー判断）。段階ごとブランチ、破壊的操作禁止、`git push` は確認
- 割り込み `constraint` は実装を止めて従う

### 4.4 レビュー粒度（Codex 6.4 ＋ Cursor 4.3）
- 順序：契約・型 → 正常系最小実装 → 不変条件・反例 → 性能 → 保存・互換 → UI 接続
- D1〜D4 は 300〜500 行相当で分割。D1〜D4 のレビュー観点は「保存則・hash・契約逸脱」のみ、見た目は D10 以降
- D7 は分布 JSON と不合格条件 (a)(b) のみ
- レビュー完了前に次段階の同じ領域へ進まない

### 4.5 長時間作業と待機（Codex 6.5 ＋ 3 者共通）
- Codex・Cursor は standby ON で常時 `wait_for_message`。依頼は 1 件ずつ、並行は最大 2（Codex コア＋Cursor UI）
- 100 seed は環境×20 seed に分割、manifest・原子的書き込み・再開コマンドをレポートに残す
- 同じ失敗を 3 回繰り返したら Claude へ設計判断を求める
- Claude は日次で「今の段階・次の主担当・ブロッカー」を `docs/50_records/開発ログ.md` に 5 行で残す

## 6. チーム原則（Codex 8 を採用）
3 者の価値は同じコードを同時に書くことではなく、**一人が書き、一人が壊しにかかり、一人が製品目的との整合を判定すること**。主担当の自己申告を合格根拠にせず、再現コマンド・機械判定・別 AI レビュー・人間の目視を揃える。
