## 2. 常設チャネル（辺）— 誰と誰が直接やりとりするか
```
             ┌────────── 設計ペア ──────────┐
   kimi(起草) ◄────────────────────────► grok(攻撃)      基本設計・契約・AT: kimi が書き grok が壊し kimi が直す。2 往復で合意しなければ Claude へ
     │  ▲                                   │  ▲
 AT/DD│  │実装の痛み                    UI設計│  │app 実装
     ▼  │                                   ▼  │
   composer(実装) ◄──────────────────────► grok            app/**: grok が遷移・敵対列を書き composer が実装、grok がマージ
     │                                       
     │ [TERM] 用語・文言                       
     ▼                                       
   glm2(第2実装) ◄── kimi(DD brief/レビュー) ── Codex(ルーター: 催促・CI・環境)
                                                  │
   Claude ◄── [escalate] のみ ── 全員          オーナー ◄── 日次要約 ── Claude
```

| 辺 | 内容 | メッセージ |
|---|---|---|
| **kimi ⇄ grok（設計ペア）** | 基本設計の章は原則 kimi 起草 → grok 敵対 → kimi 修正。**例外（起草者）**: BD-01/09/ADR/trace=Claude、BD-02=gemini、BD-11=grok（grok 起草章の敵対は kimi）。マージは basic/** の責任者 Claude（運用ルール §3.5） | `[BD-xx][review-request]` / `[review]` / `[re-request]` |
| **kimi → composer（AT/DD）** | kimi が受入テストを red で先に書き、DD を審査。composer は AT を通す | `[Dn-xxx][brief]`（kimi が出す）/ `[tests-ready]` |
| **composer → kimi（実装の痛み）** | 実装中に設計が曖昧・矛盾なら composer が kimi に直接問う。kimi が DD を直す | `[Dn-xxx][question]` |
| **grok ⇄ composer（UI ペア）** | grok が画面遷移・敵対列・受入ケースを書き、composer が app を実装、grok が審査・マージ | `[UI-xxx][brief]`（grok が出す） |
| **kimi ⇄ grok → Claude（バトル）** | 往復上限は運用ルール §3.7 の **3 ラウンド**が正（本書の「2 往復」は廃止）。3 ラウンドで合意しない論点は両者の主張を並べて Claude へ。Claude が決めて ADR に書く | `[BD-xx][escalate] A案=… B案=…` |
| **全員 → kimi（言葉）** | 新語は kimi に依頼。kimi は glossary を更新し文言を返す | `[TERM][request]` |
| **マージ責任者（記録）** | merge 時に開発ログへ 1 行。日次 PR 要約は Claude の 2h ティックに統合 | `[merged]` → `[LOG]` |
| **全員 → Codex（環境）** | CI 失敗・ツール不在・GitHub 設定は Codex。Codex は判断せず手順で直す | `[ENV][request]` |
| **Codex → 全員（催促）** | 放置 PR の催促、マージ条件そろいの通知 | `[nudge]` / `[ready-to-merge]` |
| **Claude ⇄ オーナー** | 日次要約、判断依頼（要件・RFC・境界外） | — |

kimi: AT(red)+DD 審査 ──brief──► composer: 実装 ──review-request──► kimi(契約) & grok(敵対)
                                                  ◄──review────────┘

## 5. 役割の定期最適化（固定しない）
- **周期**: 2 時間ごと（Claude の定期ジョブ）＋ 各 D 段階の完了時
- **入力（計測値）**: PR ごとの ①レビュー指摘の正解率 ②レビュー着手までの時間 ③writer の差し戻し回数 ④「反映した」報告と diff の不一致回数 ⑤マージまでの時間 ⑥bus の無駄 post 数
  - **正解率の定義**: 分母 = その reviewer の **blocker / major** 指摘（minor / nit は数えない）。不正解 = writer の rebuttal を **マージ責任者が採択**した指摘。判定時点 = PR マージ時。GitHub 上は全員同一アカウントなので集計の join キーは本文先頭の `[reviewer: <name>]`（無いコメントは集計外）
  - 集計: `scripts/team_metrics.py`（H2）。それまでは **Claude が 2h ティックで集計**して `docs/50_records/metrics/YYYY-MM-DD.md` に置く。**計測データが無い回は改版しない**
- **凍結**: open PR・進行中カードの reviewer とマージ責任者は変えない（往復カウントと writer を壊さないため）。役割改版の適用は **段階（Dn / BD 章）完了時**、または当該 AI にカードが無い時のみ
- **判定規則**:
  - 指摘正解率が 2 回連続で 50% 未満 → その領域のレビュアーを交代
  - 誤報（④）が 1 段階で 2 回 → writer から外し、手順仕事へ
  - レビュー着手 > 60 分が続く → ペアの相手を変えるか Codex の催促間隔を短縮
  - 実装 writer の初回 pass 率が高い → 担当領域を広げる（composer が D2 で良ければ D3〜）
- **出力**: 本文書 §1/§2 を改版（PR）し、全員に `[ROLE][constraint]` で再配布。変更理由は計測値で書く。**マージ責任者を動かす場合は運用ルール §3.5 を同じ PR で改定**
- **オーナーへの報告**: 日次要約に「役割変更あり／なし」と根拠 1 行
