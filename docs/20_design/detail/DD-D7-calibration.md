## 1. 較正バッチ（確定）

- コマンド: `sim-cli batch --suite calibration`（DD-D6 のバッチ基盤を流用）
- 構成: 4 環境 × 100 seed、各 2,000 tick。`batch_base = 1_000`（seed = 1000..1099。煙試験の 42..61 と重複させない。初期仮説）
- ペア試験（REQ-GEN-07）: `--suite pair`、carcass_pulse × 100 seed、系統はアカバエ・クロシデのみ（DD-D4 §1 プリセットの id 2,3 の部分集合。D7-Q2 裁定済。§10）
- 出力: DD-D6 §3 の分布 JSON に加え、10 tick 平均の時系列（系統別総生体量を 10 tick ごとに記録。AT-D7-06 の機械定義が要求）を run レコードに含める

## 2. 統計量の機械的定義（確定）

- **中央値**: 100 値を昇順ソートし `(v[49] + v[50]) / 2`（ゼロ方向丸め）。計算は i64 / Fixed のみで行い、f32/f64 を使わない
- **順位**: 環境ごとに系統の終端生体量中央値を降順。同率は id 昇順（小さい id が上位）
- **勝者**: Fixed 成立時に `share ≥ 70%` を 200 tick 連続で満たした系統（DD-D4 §2.1 の Fixed 判定系統）と同定する
- **固定率(L)**: 当該環境の 100 run 中、終了ラベル Fixed かつ勝者 = L の run 数 / 100。分母は計画数 100 で固定し、panic 等の失敗 run は非 Fixed として分母に含める
- **固定率 1 位**: 環境ごとに、固定率が最大かつ > 0 の系統（同率は id 昇順で先頭）。全系統の固定率が 0 なら「1 位なし」
- **A 型 / B 型 / C 型**（center_rich の 100 run に対して）: A = Coexist、B = Fixed かつ勝者 = アオシキ、C = Extinct。位置条件は課さない（D7-Q1 裁定済。§10）
- **出来事 3 種**（REQ-GOAL-03）の機械定義は BD-08 §7 AT-D7-06 の (a)(b)(c) をそのまま採用し、判定に必要な入力は台帳（ReasonCode 集計）・終了ラベル・10 tick 平均時系列・region 栄養（θ = DD-D4 どおり初期中央値の 10%）とする

## 3. 合否判定（確定。REQ-ACC-04）

以下を全て満たすとき D7 通過:

1. **AT-D7-01**: 400 run 全体で 2 種以上の終了ラベルが出現（REQ-SCOPE-06）
2. **AT-D7-02（上位互換。REQ-GEN-05）**: (a) 4 環境中 3 環境以上で中央値 1 位の系統が存在しない、かつ (b) 全環境で中央値 2 位以内かつ固定率 1 位の系統が存在しない。固定率 1 位の定義は §2（環境ごと・最大かつ > 0・同率 id 昇順・全 0 なら 1 位なし）
3. **AT-D7-03（ニッチ。REQ-GEN-06）**: 各系統が中央値 1 位になる環境が 1 つ以上
4. **AT-D7-04（分布帯。REQ-END-05）**: center_rich で A ≥ 10%、B ∈ [5%, 20%]、C ≥ 5%
5. **AT-D7-06（出来事。REQ-GOAL-03）**: 3 種が center_rich の 100 run 中に各 1 本以上（A/B/C 型と同じ母集団。(c) は同条件のため環境を center_rich に固定する）

**ペア試験（REQ-GEN-07）は通過条件に含めない**。carcass_pulse での両者合計固定率（Fixed で終了した run 数 / 100）が 80% 超の場合、REQ-GEN-07 の P1 調整トリガとして変換効率を下げる調整対象とし、manifest の `change_reason` 付きで記録する（REQ-ACC-04 の通過条件ではない）

判定は JSON を入力とするスクリプト（`scripts/judge_calibration.py`）が機械的に行い、人の目検を挟まない（REQ-OPS-02b）

## 4. manifest（確定。REQ-OPS-02b、AT-D7-05）

`docs/50_records/calibration/manifest.jsonl` に 1 実行 1 行で追記（append-only）:

```json
{
  "run_id": "cal-2026-08-30-01",
  "git_sha": "<40hex>",
  "config_hash": "<§4.1 の正規化列の sha256>",
  "model_version": "<実装時の World.model_version を書く>",
  "batch_base": 1000,
  "verdict": { "at_d7_01": true, "at_d7_02": true, "at_d7_03": false, "at_d7_04": true, "at_d7_06": true, "pair_fixed_rate": 0.41 },
  "distribution": { "center_rich": { "A": 0.12, "B": 0.08, "C": 0.31 } },
  "change_reason": "初回実行（変更なし）"
}
```

`change_reason` は調整時に「動かしたパラメータ群と理由」を必須記録する

### 4.1 config_hash の正規化列（確定）

`config_hash = sha256( E1 || E2 || E3 || E4 || L || M )`。連結順と各要素のバイト列は以下で固定する:

| 要素 | バイト列 |
|---|---|
| E1..E4 | 4 環境プリセット JSON ファイルの**生バイト**を environment_id の ASCII 辞書順（carcass_pulse, center_rich, edge_sparse, local_waste）に連結 |
| L | 系統プリセット `lineages_v1.json` の生バイト |
| M | `model_version` 文字列の UTF-8 バイト列（例: `d3-v1`） |

プリセットファイルはリポジトリ上で正規化済み（UTF-8・LF・キー順固定・末尾改行なし）であることを schema / フォーマット検査で担保し、ハッシュ計算時に再正規化しない（入力バイトの一意性はファイル側で保つ）

## 5. 調整ループの規則（確定。v1.0 §2.3、v0.5 §7.6）

1. 一回の調整で動かすパラメータ群は **一つ**（例: アオシキの intake のみ）。config hash・分布・理由を manifest に保存
2. **勝者補正は無条件で禁止**（REQ-OPS-03、REQ-GEN-03。直前の実行で 1 位だった系統を弱める・敗者を強める方向の調整は、理由の有無にかかわらず行わない）
3. 許される調整は案 A の軽い戻しに限る（v0.5 §7.6: アオシキ摂取 1.05→1.10、またはアカバエ摂取 1.15→1.10）。B 型 0 本でも案 B へ切替えない
4. 調整トリガ（ゲートではない）: アオシキ終端シェア中央値 50% 超 → 維持 +0.10（v0.5 §1.9）。ペア 80% 超 → 変換効率を下げる（REQ-GEN-07。§3）
5. 5 日ごとに判断: ①調整継続 ②形質／環境契約を修正して D4 へ戻る ③代表史をモデルの自然な結果へ更新
6. **15 人日を超えたら**代表史 B 型（アオシキ中央固定）を別型へ置換して収束（v1.0 §2.3）
