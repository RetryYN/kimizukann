# 設計工程 v0.3（設計を「検証できる成果物」に固定する）

作成: Claude（2026-08-30）。v0.2 却下理由「設計工程がざる」への回答。
原則: **設計とは、実装前に「何が正しいか」を機械で判定できる形にすること**。散文の設計は設計と認めない。設計成果物は必ず「それを検証するテスト設計」と対で完成し、設計レビューを通らない限り実装列に入らない。

## 0. 現状の設計の穴（D0/D1 を例に）
| 穴 | D1 で起きたこと |
|---|---|
| アルゴリズムが未設計（散文のみ） | phase の中身を Codex が実装時に決めた → 定数直書き、energy の単位混同 |
| 事前・事後条件が無い | 空実装が「仕様違反」と判定できなかった |
| 数値設計が無い | i64/scale 1e6 で 64×64 のとき総質量の上限・乗算の桁が未検討（オーバーフロー境界が不明） |
| 状態遷移が無い | Extinct/Fixed/Coexist の判定時点をレビューで後付け |
| 境界値表が無い | 余り 1u の行き先がレビューで後付け |
| 性能予算が無い | 64×64×2000 tick×100 seed が何秒か誰も知らない |
| 設計レビュー工程が無い | 契約 → 実装へ直行 |

## 1. 設計の 5 段階（各段階に「出力」「検証」「担当」「合格条件」）
```
S1 要求仕様  → S2 ドメインモデル → S3 アーキテクチャ設計 → S4 詳細設計 → S5 設計検証・凍結 → (実装)
```
下位段階は上位の ID を必ず参照する。上位を変えるときは RFC（§6）。

### S1 要求仕様（SRS）`docs/20_design/srs.md`
- **出力**: 原子的要求 1 行 1 ID。形式 `REQ-<領域>-<番号>: <主語> は <条件> のとき <振る舞い> [検証方法: AT/UT/計測/目視]`
  - 機能要求（v0.5 の各条項を分解。1 条項→平均 3〜6 要求）
  - 非機能要求: 性能（64×64×2000 tick ≤ N ms）、メモリ、決定性（三経路＋クロス OS）、保存互換、電池、APK サイズ
  - 制約: i64 固定小数点、Rust/Flutter、Android 直配布
- **検証**: 各 REQ に「検証方法」欄が埋まっていること。埋まらない要求は SRS に入れない（曖昧要求の排除）
- **担当**: Claude（起草）、kimi（検証可能性の審査）、オーナー（優先順位 sign-off）
- **合格**: 検証方法なしの REQ = 0、REQ 間矛盾 = 0（kimi が対照表を作る）

### S2 ドメインモデル `docs/20_design/domain/`
- **出力**
  1. `context-map.md`: 境界づけられたコンテキストと関係（SimCore / Calibration / Presentation / Distribution、腐敗防止層 = FFI）
  2. `glossary.md`: ユビキタス言語。語 / 定義 / 型 / 単位 / 値域 / 出典 REQ
  3. `aggregates.md`: 集約ごとに「ルート・値オブジェクト・**不変条件（式で書く）**・違反時の挙動（Err か panic か）」
  4. `state-machines.md`: 状態機械を **表**で書く（状態 × イベント → 次状態・ガード・アクション）。対象: Run（Init→Running→Terminated(label)）、Cell の占有（Empty→Occupied→Vacant→Reoccupied）、Lineage-in-cell（Present→Starving→Dead）
  5. `events.md`: ドメインイベント一覧（名前・発行 phase・ペイロード・購読者）
- **検証**: 不変条件は proptest の property として **そのまま書ける式**であること。状態機械の表から「全状態×全イベント」の網羅テストを生成できること
- **担当**: kimi（設計）、gemini（用語）、Claude（REQ との突合）
- **合格**: すべての REQ が ≥1 の集約/状態機械/イベントに対応、glossary 未登録語 0

### S3 アーキテクチャ設計 `docs/20_design/arch/`
- **出力**
  1. `modules.md`: crate/モジュール分割、**依存方向の規則**（sim-types ← sim-core ← sim-cli、逆依存禁止。CI で cargo-deny/自作チェック）
  2. `interfaces.md`: 公開 API を **シグネチャで**書く（Rust の `pub fn` 宣言と doc comment に事前・事後条件）。FFI の C ABI、schema の JSON Schema。すべて semver 管理
  3. `numeric-model.md`: **数値設計**。scale、各量の上限（例: 総質量 ≤ 2^62/scale、セル数 4096、系統 8 → 乗算の最大桁）、i128 に上げる箇所の列挙、丸め規則、余りの行き先、オーバーフロー時の挙動。**証明: 各 phase の最大中間値が i128 に収まる計算を表で示す**
  4. `determinism-model.md`: 走査順（row-major、系統 id 昇順）、乱数ストリームの割当（どの phase がどの stream を何回引くか）、浮動小数点禁止、HashMap 禁止（順序不定）、並列化するなら決定的リダクション
  5. `persistence.md`: SaveEnvelope、schema_version と model_version の bump 規則、**migration 方針**（旧 save を読むテストを必須化）
  6. `performance-budget.md`: 段階ごとの予算（tick あたり µs、64×64×2000 tick の秒数、100 seed バッチの分、APK サイズ）と計測方法（criterion）
  7. `adr/NNNN-*.md`: 決定記録（文脈・選択肢・決定・結果）。既存の決定（i64 固定小数点、xoshiro、SHA-256、GNU toolchain）を遡って書く
- **検証**: interfaces.md の宣言と `sim-types`/`sim-core` の `pub` 項目が一致（CI で `cargo public-api` 差分チェック）。numeric-model の上限が UT の境界値になっている
- **担当**: kimi（S3-1〜5）、Claude（ADR・性能予算）、grok（依存規則・決定性の抜け穴）
- **合格**: public-api 差分 0、数値上限の証明表が全 phase 分ある、ADR が既存決定を網羅

### S4 詳細設計 `docs/20_design/detail/<ID>.md`（ストーリー単位、実装の brief を兼ねる）
テンプレート（全項目必須。空欄があれば DoR 不成立）:
```
# DD-<ID>  <題>                           参照: REQ-…, DOM-…, CON-§…, ADR-…
1. 目的と範囲（触るモジュール／触らないモジュール）
2. 入力・出力・型（interfaces.md の宣言を引用。新規 pub があれば S3 を先に改定）
3. アルゴリズム（擬似コード。ループの走査順、分岐、丸め、余りの行き先を明示）
4. 事前条件 / 事後条件 / 不変条件（式。各条件に対応する UT/AT の ID を右に書く）
5. 境界値・例外表（入力の端: 0, 1u, 上限, 上限+1 / 系統 0,1,8 / 空セル …／各行に期待値と根拠）
6. 数値解析（最大中間値、使用ビット幅、numeric-model.md の上限との照合）
7. 決定性（使用する乱数 stream と回数、走査順）
8. 状態遷移への影響（state-machines.md のどの遷移を実装するか）
9. 性能見積（計算量、予算との比較）
10. テスト設計（表: テスト ID / 種類 unit·property·golden·integration / 検証する条件 / 入力 / 期待）
11. 変更影響（trace の逆引き: この DD が変える下流と、既存 golden への影響）
12. 未決事項（あれば実装に入れない。RFC へ）
```
- **担当**: writer（composer）が起草、kimi が §4/§5/§10 を審査、Claude が §6/§7/§11 を審査
- **合格**: 設計レビュー（S5）を通過

### S5 設計検証・凍結
1. **静的レビュー**（チェックリスト `docs/20_design/checklists/dd-review.md`、全項目 yes/no/n.a. で記録）
   - 事後条件は式か／各条件にテスト ID があるか／境界値表に 0・1u・上限・上限+1 があるか／余りの行き先が明記か／乱数消費が記録されているか／数値上限の照合があるか／glossary 外の語がないか／REQ 参照が実在するか
2. **実行可能検証**
   - **参照モデル**: 重要アルゴリズム（拡散、質量収支、終了判定）は Python の素朴実装（`ref/`）を kimi が DD から独立に書き、Rust 実装と **結果一致テスト**（N-version）。DD の曖昧さは両実装の食い違いとして表面化する
   - **property test の先行作成**: §4 の不変条件を proptest に落として commit（red 状態）
   - **状態機械テストの生成**: state-machines.md の表からテストを生成（`scripts/gen_sm_tests.py`）
3. **凍結**: レビュー合格で DD に `status: frozen v1` を付け、以後の変更は RFC。実装が DD から逸脱したら PR は不合格（reviewer が DD と突合）
- **担当**: レビュー = kimi + Claude（両方の approve 必須）、参照モデル = kimi、抜け穴 = grok
- **合格**: チェックリスト全 yes、参照モデルと property test が red で存在、trace 更新済み

## 2. 設計成果物とテストの対応（設計はテストとセット）
| 設計成果物 | 対になるテスト | 誰が先に書く |
|---|---|---|
| SRS の REQ | AT（受入） | kimi |
| 集約の不変条件 | property test | kimi |
| 状態機械表 | 生成テスト（全遷移） | 自動 |
| interfaces.md | public-api 差分、契約テスト（FFI/schema） | CI |
| numeric-model の上限 | 境界値 UT（上限、上限+1 で Err） | writer |
| DD §3 アルゴリズム | 参照モデル一致テスト | kimi |
| DD §5 境界値表 | 表の各行 = 1 UT | writer |
| performance-budget | criterion ベンチ＋しきい値 | writer |
| persistence の migration | 旧 save 読込テスト | writer |

## 3. 設計変更の一本道（更新・改善を安全にする）
```
RFC（docs/20_design/rfc/NNNN.md: 動機・変更・影響分析(trace 逆引き)・移行・ロールバック）
 → 影響を受ける SRS/DOM/ARCH/DD を同じ PR で改定（ID は維持、版を上げる）
 → 影響を受けるテストを先に更新（red）
 → 実装 → golden 更新（Claude 承認）→ CHANGELOG
```
- 契約・schema・FFI の変更は必ず semver bump。互換性が壊れるなら migration とテストが RFC の必須項目
- 「小さい修正だから RFC 不要」は無し。1 行でも RFC（テンプレは 10 行で済む）

## 4. 粒度
- ストーリー = DD 1 枚 = PR 1 本 ≤ 300 行（テスト込み）。D2 は 4〜6 ストーリーに割る（例: 近傍定義／拡散 1 プール／余り処理／4 プール／対称性・保存 AT／性能）
- DD 1 枚の設計→レビュー→凍結は 1 日以内を目安。超えるなら分割
