# 開発ハーネス案 v0.1（CI・機械ゲート・運用プロトコル）

作成: Claude（2026-08-30）。前提: AI チーム開発。**AI の自己申告は信用しない**。合否は機械が出し、人間（オーナー）は境界外の判断だけ行う。

## 0. D1 で起きたこと（設計の動機）
| 事象 | 人力で拾った | 機械で拾うべき方法 |
|---|---|---|
| 7 phase が空実装でテスト pass | Claude がコードを読んで発見 | 「値が変化する」assert、ゲート自己試験（§3.4） |
| 「6 点反映」報告のうち 2 点未反映 | Claude が diff を見て発見 | result に CI run URL 必須、PR 差分の機械チェック |
| テスト期待値の誤り | Claude 環境で実行して発見 | CI が全環境で実行（writer 環境に依存しない） |
| link.exe 不在 / Smart App Control | 手作業で環境修正 | CI を正本にし、ローカル実行不能でも合否が出る |

## 1. 全体構成（4 層）
```
L0 ローカル pre-commit   fmt / clippy / test / verify（数十秒）      ← writer 全員
L1 CI (GitHub Actions)   L0 + 決定性クロス OS + schema + ゲート自己試験  ← 合否の正本
L2 マージ規約            task ブランチ → PR → CI green + Claude approve → main
L3 反ゲーミング規則      テスト先行・golden 更新の権限分離・変化 assert
```

## 2. L0: ローカル pre-commit
- `.githooks/pre-commit`（`git config core.hooksPath .githooks` を README で指示）
  1. `cargo fmt --check`
  2. `cargo clippy --workspace -- -D warnings`
  3. `cargo test --workspace`
  4. `cargo run -p kimizukann-sim-cli -- verify --suite quick`（数秒で終わる縮小版）
- 落ちたら commit 不可。回避（`--no-verify`）は禁止事項として constraint 配布。
- Windows で Smart App Control に exe がブロックされた場合は L0 を skip してよい（L1 が正本）。

## 3. L1: CI（GitHub Actions）
### 3.1 `rust.yml`（push / PR、全ブランチ）
| job | OS | 内容 |
|---|---|---|
| lint | ubuntu | fmt --check、clippy -D warnings |
| test | ubuntu, windows(gnu) | `cargo test --workspace` |
| verify | ubuntu, windows | `verify --suite all` → `report.json` を artifact 保存、非 0 で fail |
| determinism-xos | (test の後) | ubuntu と windows の `state_hash` を突き合わせ。**不一致で fail**（契約 §10 三経路 + クロス OS） |
| schema | ubuntu | `docs/contracts/schema/*.json` を ajv でコンパイル、`configs/**/*.json` を検証 |
| gate-selftest | ubuntu | §3.4 |
| golden | ubuntu | `docs/contracts/golden/*.json`（seed→hash）と実行結果を比較 |

### 3.4 ゲート自己試験（gate-selftest）
ゲートが「壊れた実装を落とせるか」を CI で毎回確認する。
- `scripts/mutate.sh <name>` が意図的な破壊パッチを当てる（例: 質量係数 0.70→0.71、余りを捨てる、phase 順を入替、hash から PRNG state を外す）
- 各 mutation に対し `verify --suite all` が **fail すること**を assert。1 つでも pass したら CI 全体を fail
- これで「テストが通る空実装」「自明なテスト」を機械的に弾く

## 4. L2: マージ規約
- ブランチ: `task/<ID>`（例 `task/D2-diffuse-001`）。main への直接 push 禁止（branch protection、オーナー設定）
- PR 必須。PR 本文テンプレ: brief ID / 触ったファイル / `git diff --stat` / CI run URL / 未解決事項
- マージ条件: CI 全 job green ＋ reviewer approve（kimi）＋ gate approve（Claude）。CODEOWNERS で `docs/contracts/**` と `docs/contracts/golden/**` は Claude 必須
- result メッセージ形式（改定）: `[ID][result] status=pass pr=<url> ci=<run-url> diff=<n files/+a/-b>` — **CI URL の無い result は受理しない**

## 5. L3: 反ゲーミング規則（constraint として全員に配布）
1. **テスト先行**: 各 Dn は kimi が受入テスト（`tests/gate_Dn.rs`）を先に書き、writer はそれを通す。writer は受入テストを編集不可（CODEOWNERS）
2. **golden の更新は Claude 承認のみ**。hash が変わる変更は PR に理由を書く
3. **変化 assert**: 状態が更新される phase は「初期値から変化した」を必ず assert
4. `--no-verify`、`#[ignore]`、`allow(clippy::…)` の追加は禁止（例外は brief に明記）
5. 報告は CI が出した数値だけ。自分の環境の結果は参考値

## 6. 運用の自動化（helix-bus 連携）
- `scripts/ci-report.mjs`: `gh run watch` の結果を `[ID][ci] status=... url=...` として claude に post（Claude の Monitor が拾う）
- `bus-ctl log`: brief / result / review を `docs/相談会/開発ログ.md` に自動追記（今は Claude が手書き）

## 7. 要件定義との順序
ハーネス完成後に D2 以降の brief を出す。以後の brief は必ず「**合否条件 = §3.3 の該当行 + 受入テストのファイル名**」を含み、要件定義（v0.5 の各条項）→ 受入テスト → 実装 の順（ATDD）を固定する。
