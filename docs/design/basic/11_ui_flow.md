起草: grok。審査: kimi。対象段階: D12。コアは wall clock を読まない。再生・画面・保存タイミングは Presentation の責務。FFI シグネチャの確定値は BD-05。本章の FFI 欄は v1.0 7.1 の 7 操作名に合わせた **初期仮説**。

## 1. 画面と一巡

### 1.2 仮説の 6 択と禁止

参照: REQ-UI-06, REQ-UI-02, REQ-EXP-06

心配なこと（表示順は固定。seed で並べ替え・強調しない）:

| 表示文 | 判定の観測（v0.5 7.5） |
|---|---|
| 食べ物を使い切りそう | nutrient の負の z＋飢餓由来死亡 |
| 増えすぎて、あとで一気に減りそう | 繁殖急増→維持不足→死亡急増 |
| 汚れがたまりそう | waste 正の z、toxin_sensitive 維持コスト増 |
| 死骸がうまく使われなさそう | carcass 蓄積、use_carcass 系統の未到達 |
| 逃げる場所がなくなりそう | 空き家増でも当該系統が局所に残る |
| みんな同じ場所に集まりそう | 高生体量セルの系統間重複率が閾値超 |

対応スタンプが score ≥ 1.2 で 1 件以上→「起きた」。0 件かつ終了→「起きなかった」。観測窓不足→「まだわからない」。禁止: 正解数、ランク、「別 seed」「固定された偶然」「毎回こうなる」。

## 2. 再生スケジューラ（7 要素）

参照: REQ-UI-03, REQ-CON-05, REQ-DET-07, REQ-UI-04a, REQ-UI-04b, REQ-VIS-04

コアは `step(n)` のみ。速度変更・一時停止は PRNG を消費しない。クロックは **単調時計**（初期仮説。`DateTime.now` 禁止。端末時刻改変で tick を飛ばさない）。

速度（確定）: 低速 1／標準 4／高速 16 tick/s。一時停止は 0 tick/s。

| # | 要素 | 条件 | 動作 | 検証ケース | AT |
|---|---|---|---|---|---|
| 1 | 速度と一時停止 | ユーザーが 1/4/16/停止を選ぶ | 目標 tick/s だけ変える。`step` の引数と PRNG は速度に依存しない | 同一 config・seed を 3 速度＋途中停止で 2,000 tick まで進め、最終 hash・終了ラベル・イベント列がビット一致 | AT-D12-SCH-01 |
| 2 | 固定時間刻み | フレーム時刻 `t`、前フレーム `t0`、目標 `r` tick/s | `due += r * (t-t0)`。刻みは `r` の逆数に固定し、フレーム間隔の実測で `due` だけ積む | 模擬 60 Hz 完全周期で 4 秒（標準）→ 実行 tick=16±0（許容は BD-08 で数値化。初期仮説 ±0） | AT-D12-SCH-02 |
| 3 | フレーム実行上限 | 1 フレームで `due` が上限を超える | このフレームの `step` 合計は 低速 1／標準 1／高速 2。残りは `due` に残す | 1 Hz フレーム×高速で 1 フレームに `step(2)` まで。`step(16)` 一括は禁止 | AT-D12-SCH-03 |
| 4 | 遅れ持ち越し | 上限で切り捨てた `due` | 次フレーム以降に加算。リセットしない | 遅れ 5 tick を作ったあと通常フレームに戻し、累積実行 tick が目標に追いつく（描画は遅れてもよい） | AT-D12-SCH-04 |
| 5 | 描画間引き、tick 非破棄 | `due` が上限より大きい | `step` は上限まで実行。`snapshot` と Flutter 描画を 1 フレーム省略可。間引きはリプレイに載せない | 間引き有無で state hash 一致（REQ-VIS-04）。高速中の同一 stamp id 重複描画なし | AT-D12-SCH-05 |
| 6 | 500 ms 自動一段下げ | 単調時計の累積遅れ ≥ 500 ms（確定） | 16→4、4→1。1 のままなら停止はしない（初期仮説: 低速を維持し遅れを持ち越し） | 人工 200 ms/フレームで 3 フレーム後に一段下がる。手動で上げ直したら累積遅れを 0 に戻す（初期仮説） | AT-D12-SCH-06 |
| 7 | 凍結 | 一時停止 **または** S-NOW/S-STAMP 表示中 **または** OS 中断（inactive/paused/detached） | `due` を積まない。`step` しない。単調時計の基準を再開時に引き直す | 説明 overlay を 2 秒開いても tick が進まない。閉じた直後に `step` バーストしない | AT-D12-SCH-07 |

追加ケース（v1.0 7.3）:

| AT | 入力 | 期待 |
|---|---|---|
| AT-D12-SCH-08 | 模擬フレーム列 30 Hz と 120 Hz、標準 4 tick/s、60 秒 | 実行 tick が `4*60` に対し許容差内（初期仮説: ±2 tick。BD-08 で確定） |
| AT-D12-SCH-09 | 高速 16、スタンプ多発 seed | 同一 `event_id` の皿上ピンが同時に 2 個以上に増えない |

保証（確定、実機）: 基準端末・標準・手動停止なし・OS 中断なしで 2,000 tick を 8 分 20 秒以内、開始前操作＋終了表示込み一巡 10 分以内（REQ-UI-04a）。最低対象端末・高速で 2,000 tick を 2 分 10 秒以内（REQ-UI-04b）。headless 1 秒はユーザー再生に出さない。

スケジューラ検証ケース数 **9**（SCH-01…09）。

## 3. 中断復帰（3 速度 × hash 連続）

参照: REQ-UI-05, REQ-DET-07, REQ-DET-02, REQ-DET-06, REQ-CON-08

用語: `H(t)` = tick `t` 終了時点の正規化 state hash（描画トークン・UI・ログ時刻を除く。契約 §10）。

### 3.1 シーケンス（速度 V ∈ {1, 4, 16}）

1. S-RELEASE で `create`。`save` → `H(0)` をローカルに書く。
2. 速度 V でスケジューラ運転。中断点 tick `t`（AT は 1,000 と乱択数点。REQ-DET-02）。
3. OS 中断またはプロセス終了の検知: 要素 7 で凍結 → 進行中 `step` の完了を待つ（初期仮説: 呼出は同期、待たずに kill されたら BD-11 §3.2）→ `save` → 書込完了を確認 → 必要なら `destroy`。
4. プロセス再起動 → S-BOOT → `load`。checksum / `schema_version` / `model_version` 不一致は S-ERR。成功後 `snapshot` で `H_load` を読む。
5. `H_load == H(t)`（連続）。速度 V のまま残りを終了まで進める。
6. 対照: 同 config・seed を中断なしで終了まで。最終 hash・終了ラベル・イベント列が一致（REQ-DET-07）。

| AT | V | 中断 | 期待 |
|---|---|---|---|
| AT-D12-RES-01 | 1 | tick 1,000 で `paused` → kill → 再起動 | `H_load=H(1000)`。最終三要素が連続運転と一致 |
| AT-D12-RES-02 | 4 | 同上 | 同上 |
| AT-D12-RES-03 | 16 | 同上 | 同上 |
| AT-D12-RES-04 | 4 | tick 乱択（初期仮説 3 点）で同じ手順 | 各点で hash 連続 |

`save` バイトは呼出側バッファ。容量不足は required length を見て再確保し、成功するまで中断完了としない。参照: REQ-CON-08。

### 3.2 書込途中 kill

参照: REQ-DET-06, REQ-CON-08

初期仮説: 一時ファイルへ書いてから rename。不完全ファイルは `load` が checksum で失敗し S-ERR。自動ロールバックは直近の成功セーブのみ。部分バイトを `load` して handle を作ることは禁止。

## 4. FFI 7 操作: 呼出順と失敗

参照: REQ-CON-01, REQ-CON-05, REQ-CON-08, REQ-DET-06

生存 handle は同時に **最大 1**（初期仮説。BD-05 が別値を置いたら従う）。可変長は呼出側バッファ。不足時はエラー＋ required length。ポインタを Dart へ渡さない。

### 4.1 成功経路の順

| 経路 | 順 |
|---|---|
| 新規一巡 | `create` → `save` →（`step` → `snapshot`）* →（`explain`）* → `save` → `destroy` |
| 再開 | `load` → `snapshot`（連続確認）→（`step` → `snapshot`）* →（`explain`）* → `save` → `destroy` |
| 1 フレーム（運転中） | 凍結でなければ `step(k)`（`k`≤要素 3 の上限）→ 間引きしなければ `snapshot` → 描画。`explain` はユーザー操作時のみ |
| 中断 | 凍結 → 進行中呼出の戻り待ち → `save` → 確認 →（終了するなら）`destroy` |

禁止順: `destroy` 後の任意呼出。`create`/`load` 成功後に旧 handle を捨てない。`step` と `save` の並列。`explain` 中の `step`（画面が S-NOW/S-STAMP なら要素 7 で `step` しない）。

`step(n)` の `n` はスケジューラだけが決める。UI ボタンから `step(2000)` を直接叩かない（REQ-CON-05）。

### 4.2 失敗時

| 操作 | 失敗 | UI | handle |
|---|---|---|---|
| `create` | config schema 違反、NumericError | S-ERR。仕込みへ戻す | 作られない |
| `load` | checksum / schema_version / model_version 不一致、破損 | S-ERR。破棄は明示 | 作られない |
| `step` | NumericError、死んだ handle | 凍結。S-ERR。最後の成功 `save` を残す | `destroy` を試みる |
| `snapshot` | バッファ不足 | required length で再呼出。2 回目失敗は描画スキップ（tick は捨てない） | 維持 |
| `explain` | 不明 `event_id`、バッファ不足 | 不足は再呼出。不明は「この印の説明を用意できなかった」テンプレ。core 状態は変えない | 維持 |
| `save` | バッファ不足、ディスク満杯 | 不足は再呼出。ディスク失敗は中断完了にしない。再試行 1 回（初期仮説） | 維持 |
| `destroy` | 二重 destroy | 無視して成功扱い（初期仮説） | なし |

AT: AT-D12-FFI-01 バッファ不足 2 段。AT-D12-FFI-02 `load` 3 種不一致。AT-D12-FFI-03 `destroy` 後 `step` がエラー。AT-D12-FFI-04 公開面が 7 操作以外を持たない（public-api / 索敵）。

| ADV-18 | オフライン・飛行機モードで一巡 | 完了する。送信 API・権限なし（REQ-OUT-05, REQ-UI-09） | AT-D12-ADV-18 |
| ADV-19 | `explain` 失敗後に再生再開 | handle 維持。tick は説明失敗で進まない。再開は閉じたあと | AT-D12-ADV-19 |
| ADV-20 | 低速で 2,000 tick 中に 50 回中断復帰 | 各復帰で `H` 連続。最終三要素が連続運転と一致 | AT-D12-ADV-20 |

敵対列 **20**。
